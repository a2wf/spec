Why v1.1?

v1.0 was a one-page declaration. v1.1 makes it operational.

What v1.0 could not express

  • Nuanced human oversight (autonomous / confirmation / notification / handover)
  • Machine-readable jurisdictional declarations (applicable laws)
  • Agent identification protocols (DID, VC, HTTP Message Signatures, OAuth)
  • Data-handling transparency (DPV alignment)
  • Incident-reporting contact and intended timeframe
  • Discovery hints (Schema.org Actions, sitemap, rate limits)
  • Audit-trail declarations
  • Security, Privacy, Internationalisation, and Accessibility Considerations (Sections 10/11)

Liaison input that drove v1.1

  • Paola Di Maio (AIKR CG): use ODRL, reuse Schema.org, link to agent-identity standards
  • Ian Jacobs (W3C Staff): discovery via /.well-known/, not site root
Concrete example to mention: v1.0 humanVerification=true vs v1.1 oversight.oversightDefaults.regulated.level=handover. The Paola/Ian quotes are real input from earlier rounds; reference them visibly. Security/Privacy/i18n/a11y are first-class sections in the spec; mention briefly.

Three-layer architecture

+------------------------------------------------+ | Profiles (e.g. EU Governance Starter) | +------------------------------------------------+ | Modules (7 optional, normative) | +------------------------------------------------+ | Core (identity, permissions, oversight,| | discovery, conformance) | +------------------------------------------------+

Related precedents in W3C and adjacent ecosystems: ODRL Core + Profiles, DID Core + Method Specs, WebAuthn Core + Extensions, WCAG Levels. W3C specs commonly use related variability patterns; the W3C QA Framework recognises profiles, modules, and levels as legitimate techniques.

Why three layers

  • Core stays small enough that every operator can implement it
  • Modules are opt-in and bring domain depth where needed
  • Profiles bundle modules for specific markets without forcing global complexity
Be ready for "why not just use ODRL directly?" - answer: ODRL is a strong abstract policy model; A2WF is a low-friction website declaration format. A normative ODRL profile of A2WF is a v1.2 candidate. Do not oversell WCAG as a "module" precedent - it is a Levels precedent only.

A2WF v1.1 is a website declaration envelope. It reuses external vocabularies wherever stable, and adds only the minimum new shape it needs (permissions, oversight, conformance metadata).
This slide directly addresses Paola's three tips. Be ready to defend: "no NEW agent identity protocol, no NEW data-handling vocabulary, no NEW action vocabulary". The thing A2WF adds is the envelope that glues these together at a single well-known URL.

The seven Modules in v1.1

ModulePurpose
dataHandlingPurposes, retention, lawful basis, controller (DPV-aligned)
agentIdentificationAccepted identity protocols and credential types
auditTrailLightweight audit posture, retention, accessibility
incidentReportingContact + intended acknowledgement timeframe
discoverabilityHintsSitemap, Schema.org Action endpoints, rate-limit hints
jurisdictionsRegion, applicable laws (EU AI Act, GDPR, ...)
codeOfPracticeAlignmentAlignment with industry codes (not certification)

Modules are independent. A document can claim zero, one, or all seven via conformance.moduleClaims. The Core does not require any module.

"The seven modules are not seven things you have to do; they are seven shapes of declarations you can make if they apply to you." Highlight dataHandling aligns with DPV - that is the Paola hook.

EU Governance Starter Profile

A neutral example profile, published alongside the spec.

URI: https://a2wf.org/profiles/eu-governance-starter/v1

Requires these six module claims, minimally populated:

  • jurisdictions (region: EU, applicableLaws)
  • dataHandling (purposes + retention + lawful basis + controller)
  • agentIdentification (>= 1 protocol)
  • auditTrail (enabled + retention)
  • incidentReporting (contactEmail + responseTime)
  • discoverabilityHints (sitemap or actions)

What the profile is NOT

NOT a certification · NOT a compliance audit · NOT a legal claim · NOT endorsed by any EU institution

Any vendor may build tools around this profile. The constraints are: no W3C / A2WF endorsement claims; no "certified compliant"; operator keeps the raw JSON portable and can switch vendors at any time.

Anticipate "is this a back door to a paid certification market?" Answer: profile claim is publisher-declared; vendor reports MUST disclaim. The reference tools enforce this through built-in disclaimers. Customer-portability via raw JSON is the anti-lock-in protection.

Conformance model

A2WF v1.1 conformance is qualitative, not numeric.

  • A document validates to PASS, PASS+WARN, or FAIL
  • There is no 0-100 conformance score in the specification
  • Vendor tools MAY publish their own scoring products - these are vendor metrics, NOT A2WF conformance signals
  • Validator findings carry severity, a section reference, and an explanatory message
  • Conformance levels: basic and standard; profile claims add a third axis
This was a deliberate choice. Numeric scores invite false-equivalence claims ("we are at 85, that means compliant") that the framework cannot underwrite.
Strong defensible position. Mention the reference checker's score is capped at 59 on validation failure - that is the discipline we ask other vendors to apply too.

Open questions for the CG

Five questions we want directional CG input on. These are not requests for resolution in this call; they are framings for the next ~6 weeks of issue tracking. We will open them as labelled GitHub issues within 48 hours of this meeting.

  1. ODRL profile of A2WF — should v1.2 include a normative export to ODRL, or keep architectural alignment only? (Paola's first tip)
  2. Trigger expression language — permissions may carry conditions; should the expression syntax be JSONLogic, ODRL Constraints, SHACL, or remain undefined? Currently undefined.
  3. Schema.org Action vocabulary curation — we curate ~20 actions; should the CG maintain the curated set, or open it to community submissions?
  4. Cache directive precedence — the spec (Section 9.4) currently says HTTP Cache-Control / ETag / Last-Modified win, with the document-internal discovery.cache as fallback. Is this the right ordering?
  5. Multi-region jurisdictional posture — sites in multiple EU member states declare one jurisdictions.primary with an applicableLaws union. Sufficient?
Frame as "directional input over six weeks", not "resolution in one call". ODRL and trigger language especially need follow-up discussions; do not try to settle them on stage. The cache question is already partly decided in the spec; this is a check that the decision is acceptable.
